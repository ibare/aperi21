# 곡률 반지름 — 이관 기록

원본: `tasks/piece-lab/radius-of-curvature/` (자유 구현, 캔버스 직접 그리기)
이관: 엔진 어휘 위의 선언. **자유 렌더 계층(`Bundle.renderers`)을 쓰지 않았다.**

## 쓴 어휘

| 원본의 것 | 선언 |
|---|---|
| 길 (닫힌 곡선 360점) | `trajectory` · `closed` · `width 2.4` · `colorRole: 'ink'` |
| 중심이 지나는 길 (축폐선) | `trajectory` · `closed` · `width 1` · `opacity 0.17` |
| 얹힌 원 (96개 호 조각, 알파 손으로) | `trajectory` · `style.fade: 'focus'` + `focus: { at: 0.5, width: 0.103 }` |
| 반지름 선분 | `trajectory` 2점 · `width 1.6` · `opacity 0.72` |
| 원의 중심 | `body` circle · `size 3.4` · `outline: 'none'` · `glow: false` |
| 달리는 점 (종이색 테두리) | `body` circle · `size 6.2` · **`outline: 'background'`** · `glow: false` |
| 캡션 (dR/dφ 부호로 갈림) | `BundleSchema.caption` 슬롯 · `cases[{ when: 'swelling' }]` |
| 경로 위 최근접점 드래그 | `point-drag` · `binds { pos, held }` · **`snapTo: CURVE.points`** |
| 화면보다 큰 원이 잘리는 것 | `boundsHint` 고정값 + `canvas.height 400` |

## 쓴 순수 함수 (`@aperi21/plugin-mechanics`)

sim 이 직접 import 한다 — 원칙 1 이 허용하는 「도메인 plugin 의 순수 계산 함수」다.
`render*` 는 가져오지 않는다(이 plugin 에는 없다).

- `pathFromCurvatureRadius({ radiusAt, samples: 360 })` — 곡률 반지름을 **입력으로**
  주고 곡선 · 축폐선 · 호길이 표를 받는다. 원본이 지지함수 `h = 180 + 36cos2φ` 를
  세우고 `P = (h cosφ − h′ sinφ, h sinφ + h′ cosφ)` 를 손으로 짜던 자리다.
- `arcLengthAtAngle(path, 0.6)` — 시작 자리 φ 를 호길이로. 원본의 `arcAt(PHI0)`.
- `sampleAtArcLength(path, arc)` — 호길이에서 점 · 중심 · 반지름 · φ 를 한 번에.
  원본의 `phiOfArc` (뉴턴 6회) + `pointAt` + `centerAt` + `radiusAt` 네 함수를 대신한다.
- `angleAtArcLength` — 호길이를 각으로 되읽는 통로. (지금은 `angleAt` 로만 노출)

**대조 결과**: 표본 361개 전부에서 `|Δ점| < 5.2e-8`, `|Δ축폐선| < 5.2e-8`,
`|Δ호길이| < 2.8e-8`. 둘레 `1130.9734` = `2π·180` 정확히 일치, `closureGap 7.6e-14`,
`R` 최소 `72.00` 최대 `288.00`. **원본 수식과 같은 곡선이다.**

`pathFromCurvatureRadius` 는 표본의 무게중심을 원점으로 옮기는데, 이 곡선은
`P(φ+π) = −P(φ)` 로 중심대칭이라 옮김량이 정확히 원본의 원점(`−216, 0` 보정)이었다.
그래서 좌표가 그대로 맞는다.

## (a) 원본과 달라진 점과 이유

### 1. 알파 감쇠의 모양 — 가우시안 → 평탄부 + 선형

원본은 접촉점 기준 각거리로 `0.11 + 0.78·exp(−d²/2·0.55²)` 를 매겼다. 엔진의
`fade: 'focus'` 는 **반폭 안은 1, 거기서 `width` 만큼 더 가면 바닥(0.08)** 인 꼴이다.

`focus.width` 는 **알파가 절반으로 떨어지는 자리**를 맞춰 정했다 — 원본은 0.648 rad,
원 한 바퀴가 경로 전체이므로 `0.648 / 2π = 0.103`.

| 접촉점에서의 각거리 | 원본 | 이관 |
|---|---|---|
| 0.000 | 0.890 | 0.890 |
| 0.324 | 0.766 | 0.889 |
| 0.500 | 0.626 | 0.667 |
| **0.648** | **0.500** | **0.480** |
| 0.900 | 0.314 | 0.161 |
| 1.200 | 0.182 | 0.071 |
| π | 0.110 | 0.071 |

진하게 붙어 있는 구간(반치폭)은 같고, **접촉점 바로 곁이 조금 더 또렷하고 먼 쪽이
조금 더 옅다.** '국소적으로 닮았다' 는 주장은 반치폭이 지키므로 이 차이를 받아들였다.

원본이 `butt cap` + 6% 겹침으로 막던 "옅은 구간이 점선처럼 끊겨 보이는 것" 은 여기서
생기지 않는다 — 엔진은 `round cap` 이지만 도막 끝이 **맞닿아** 있어 알파가 겹쳐 쌓이는
폭이 굵기 절반뿐이다. 도막 수는 원본과 같은 96.

### 2. 종이색 테두리의 굵기 — 2 → 1

`Body.outline: 'background'` 가 긋는 굵기는 `theme.strokeWidth.thin`(=1) 고정이다.
원본은 2 였다. 점이 길·원과 겹치는 자리에서 경계를 떼어 내는 일은 하지만 조금 얇다.

### 3. 캡션 기준선 — 378 → 376

엔진의 화면 고정 앵커는 여백 24 에 `textBaseline: 'bottom'` 이다. 원본은 y=378 의
alphabetic 기준선이라 실제 글 아래끝이 ~381 이었다. 5px 차이라 보정하지 않았다.
색은 `colorRole: 'muted'` + `emphasis: 'strong'`(테마 `#6B7280`), 원본은 `#5b6472`.

### 4. 좁은 컨테이너의 축소 문턱 — W≥536 → W≥552

원본 `SC = max(0.45, min(1, (W−56)/480))`, 엔진 `scale = min(1, (W/2−36)/240)`.
여백이 28 대 36 이라 3~4% 일찍 줄기 시작한다. **W ≥ 552 에서는 완전히 같다** —
probeTimes 다섯 시각의 달리는 점 · 원의 중심 · 화면 반지름이 소수점 첫 자리까지 일치한다
(아래 표).

### 5. "화면 아무 데나 눌러" → "점을 잡아"

원본은 캔버스 어디를 눌러도 점이 그 자리의 최근접 길 위 지점으로 뛰었다. 엔진의
`point-drag` 는 손잡이 둘레 `grabRadius` 안을 눌러야 잡힌다. 20px 로 두었다. 일단
잡은 뒤의 **끌기는 원본과 같다** — `snapTo` 가 길 위로 붙이므로 급히 굽는 자리와
느슨히 굽는 자리를 손으로 왕복할 수 있다. 아래 「어휘 부족」 1번.

### 6. 시간표를 선언하지 않았다

이 조각에는 주기 안 단계가 없다. 점이 한 방향으로 계속 돌 뿐이고, 캡션은 시각이
아니라 **부호**로 갈린다. 그래서 `timeline` 없이 `caption.cases` 만 쓴다.
`startAt`/`preroll` 도 쓰지 않는다 — "도착한 순간 이미 부푸는 중" 은 `initialState`
가 호길이를 `arcLengthAtAngle(CURVE, 0.6)` 에서 시작하는 것으로 이미 성립한다.

## (c) 어휘 부족 — 다음 엔진 작업의 입력

1. **`point-drag` 에 "그림 아무 데나" 가 없다.** 판정이 손잡이 둘레 `grabRadius`
   원 하나뿐이라, 원본의 "빈 자리를 눌러도 점이 그리로 뛴다" 를 말할 수 없다.
   `grabRadius` 를 캔버스보다 크게 주면 흉내는 나지만 그건 화면 크기를 상수로 아는
   척하는 것이라 하지 않았다. 필요한 것은 **잡히는 영역의 종류**다 — 손잡이 둘레냐,
   조각이 준 점열 근방이냐, 화면 전체냐. 지금은 셋이 하나의 px 수로 눌려 있다.

2. **`point-drag` 의 손잡이가 조각의 역할색을 못 쓴다.** 조작기는 `ui` 축 색
   (`ui.text` 채움 + `ui.onSelected` 테두리, 반지름 8/10)으로 그려지고, 이것이
   scene 의 달리는 점(반지름 6.2, `primary`) 위에 **매 프레임 덮인다.** 그래서 원본의
   "원 · 반지름 · 중심 · 달리는 점이 전부 한 색" 이 이관본에서는 달리는 점만 어두운
   남색이 된다 — **색이 한 가지 뜻만 갖는다는 이 조각의 규칙이 깨진다.**
   `body` 선언은 그대로 두었다. 조작기가 조각의 그림을 손잡이로 삼을 수 있게 되면
   (예: `handle: { bodyId }` 처럼 **그릴 것을 scene 에 맡기는** 길) 그대로 맞는다.
   C2 의 축 분리와 충돌하지 않는다 — 조작기가 `scene` 색을 빌리는 것이 아니라
   **그리기를 하지 않는 선택지**가 필요한 것이다.

3. **`Body.outline` 의 굵기를 선언이 정하지 못한다.** `theme.strokeWidth.thin`(1)
   고정이다. 원본의 종이색 테두리는 2 였다. 테두리가 얼마나 두꺼워야 겹친 선에서
   경계가 떼어지는지는 그 그림의 판단이다.

4. **`fade: 'focus'` 의 감쇠 곡선이 한 가지다.** 평탄부 + 선형 하강이라 가우시안의
   어깨가 나오지 않는다. 폭을 조각이 정하게 둔 것은 옳다(원본 NOTES 의 요구).
   모양까지 고르게 할 값이 있는지는 두 번째 사례를 기다릴 일이다 — 지금은 반치폭을
   맞추는 것으로 주장이 선다.

5. **캡션 `cases` 의 부정형이 없다.** `when` 이 boolean 경로 이름이라 "부푼다" 하나만
   `cases` 로 쓰고 "오므라든다" 는 `text` 폴백으로 두었다. 둘 다 `cases` 로 쓰려면
   physics 가 서로의 부정인 boolean 둘을 상태에 실어야 한다. 지금 형태도 동작은
   같지만, 두 문장이 선언에서 대칭으로 보이지 않는다.

## (d) 화면에 두지 않은 것 — 원본의 결정을 그대로 유지

- **숫자.** 반지름 값도 곡률 값도. 붙이면 동사가 "부푼다" 에서 "값이 오른다" 로 바뀐다.
  반지름 선분의 **길이가 값**이다.
- **축 · 그리드 · 눈금.** 읽을 값이 없다. `chrome` 을 켜지 않았다.
- **접선.** 접촉원이 접선까지 물려받는다는 것은 원이 길에 겹쳐 보이는 것으로 이미 드러난다.
- **범례 · 제목 · 재생 버튼.** 움직이는 덩어리가 하나뿐이라 가리킬 것이 없다.

## (e) 의존 하나를 더했다 — 확인 필요

`sims/kinematics/radius-of-curvature/package.json` 에 `@aperi21/plugin-mechanics` 를
peer + dev 로 넣고 `node_modules/@aperi21/plugin-mechanics` 심볼릭 링크를 손으로 걸었다
(`sims/mechanics/conservation-of-mechanical-energy` 와 같은 꼴). **`pnpm install` 은 돌리지 않았다** —
`pnpm-lock.yaml` 은 다른 조각 이관과 공유하는 파일이라 메인이 합친 뒤 한 번 돌려야 한다.
