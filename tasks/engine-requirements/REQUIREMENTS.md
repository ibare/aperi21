## 1. 문제는 세 갈래다

요구사항을 한 덩이로 쓰면 안 된다. 성격이 다른 셋이 섞여 있다.

### (가) 엔진에 이미 있는데 구현체가 닿지 못한 것

| 있는 것 | 어디 | 못 닿은 증거 |
|---|---|---|
| 캔버스 부트스트랩 (DPR·ResizeObserver·CSS px) | `Canvas.tsx` | 7·8이 각자 `resize()` 재작성. 8은 "폭 계산 때문에 한 번 헤맸다" |

| 테마 토큰 · 선 두께 | `rc.theme` | 7·8이 색 리터럴 직접 사용 |

치르는 값이 아니다. 5번 `archimedes` 가 `NOTES.md` 에 "등록은 호스트가 한다"를 따로
적어 둔 것이 그 증거다.

## 2. 네 번째 문제 — 크기

앞의 세 갈래는 "무엇을 만들까" 였다. 이것은 **만든 것을 어떻게 실어 보내는가** 이고,
성격이 달라서 따로 세운다. 엔진이 커질수록 이쪽이 먼저 한계에 부딪힌다.

### 2.1 지금 얼마인가 (gzip 실측, 2026-09-09)

| 조각 하나를 여는 데 | gz | 무엇 |
|---|---|---|
| `@aperi21/host` | **20.4 KB** | 통짜. renderer 8종 + controller 6종 + camera + time + particles + runtime |
| `runtime` chunk | **4.3 KB** | 어댑터 + bootstrap |
| **eager plugin·stage** | **16.8 KB** | plugin-optics + plugin-circuit + `archimedes` **전체** + `container-shape` **전체** |
| — 고정 합계 | **41.5 KB** | |
| 조각 자신 | 2.1 ~ 6.3 KB | `ray-tracing` 2.1 / `projectile` 2.8 / `dc-circuit` 2.7 / `pressure-isotropy` 3.9 |

`projectile` 하나를 보는 독자는 **44.3 KB 중 2.8 KB만 자기가 보는 것**을 받는다.
**94 %가 엔진이고, 그중 16.8 KB는 자기가 열지도 않은 다른 조각의 코드다.**

### 2.2 발현 셋

**(1) 통짜 커널.** `packages/host/src/index.ts` 가 11개 모듈을 전부 재수출한다.
그중 `controller/` 만 1131줄이고 절반이 발사체 전용(`pinball-launcher`·`angle-dial`)이다.
슬라이더 하나 쓰는 조각도 핀볼 런처를 받는다.

**(2) eager 로드 — 조각 수에 선형.** 결정적 문제다.

```ts
// packages/bootstrap/src/index.ts — installAperi21Plugins()
await Promise.all([
  import('@aperi21/plugin-optics'),
  import('@aperi21/plugin-circuit'),
  import('@aperi21/sim-pressure-and-container-shape'),   // ← sim 전체
  import('@aperi21/sim-archimedes-principle'),           // ← sim 전체
]);
```

lazy loader 로 등록해 놓고 옆에서 eager 로 끌어온다. 이유는 **자유 렌더 계층이
`Plugin` 계약을 타기 때문**이다. `Plugin` 은 `pluginManager.register()` 로 미리
등록돼야 하고, 그러려면 모듈이 먼저 로드돼야 한다.

sim 6개 중 자유 렌더를 쓰는 2개 때문에 11.5 KB 가 항상 실린다. **조각이 600개가 되고
그중 절반이 자기 시각화를 직접 그리면 — §0 표를 보면 그게 정상 경로다 — 부트스트랩이
300개를 전부 로드한다.** 산술적으로 1.7 MB 다.

이 문제의 뿌리는 §1(가)와 **같다.** 자유 렌더가 `Plugin` 이라는 무거운 문을 통과해야
한다는 것. 그 문을 없애면 두 문제가 함께 사라진다.

**(3) 중복이 아니라 총량.** `@aperi21/host` 는 이미 `external` + `peerDependency` 다
(원칙 3). 그래서 **N배 중복은 없다.** 그러나 external 은 총량을 줄이지 않는다 —
호스트가 통짜 host 를 한 번 받을 뿐이다. 오히려 원칙 3이 총량 문제를 만든다.
"갈라지면 안 되니 하나로 묶는다" 가 "하나로 묶였으니 전부 받는다" 가 된다.

### 2.3 정체성과 능력을 가른다

원칙 3이 실제로 지키려는 것은 **정체성** 이지 코드 전체가 아니다.

| | 갈라지면 | 크기 | 정책 |
|---|---|---|---|
| **정체성** — registry Map, 계약 타입, 무대 생애 | **틀린다.** 등록한 것을 못 찾는다 | 작아야 한다 | 단일 인스턴스 강제. `external` + peer |
| **능력** — 도구, 어휘, 솔버 | **느려질 뿐 틀리지 않는다.** 상태가 없으니까 | 크다 | 자유롭게 쪼갠다. 최악의 경우 중복돼도 정확하다 |

지금 둘이 한 패키지에 있다. **정체성을 공유하려고 능력 전부를 받고 있는 것이다.**

이 구분에서 `external` 의 기준이 나온다 — **크기가 아니라 모듈 레벨 상태의 유무.**

### 2.4 20 과 80 — 트리셰이킹이 실제로 되려면

요구는 이것이다. **엔진 기능이 100이면, 뭘 만들어도 들어가는 20만 항상 실리고,
나머지 80은 그 조각이 실제로 쓴 것만 실린다.**

패키지를 쪼개는 것만으로는 되지 않는다. 지금 셰이킹이 **0인** 기계적 이유가 있다.

```ts
// packages/host/src/host.ts — Host 생성자
for (const [type, renderer] of Object.entries(CORE_RENDERERS)) {   // 렌더러 8종
  this.rendererRegistry.register(type, renderer);
}
this.controllerRegistry.register(new PinballLauncherController());  // 컨트롤러 5종
this.controllerRegistry.register(new AngleDialController());
this.controllerRegistry.register(new PlacementController());
this.controllerRegistry.register(new ValueEditController());
this.controllerRegistry.register(new SliderController());
this.computeRegistry.registerVector('uniform', uniformVectorField); // 계산 2종
this.computeRegistry.registerVector('gravity', gravityVectorField);
```

**`new Host()` 한 번이 엔진의 모든 능력을 살려낸다.** 조각이 슬라이더 하나만 써도
핀볼 런처가 실린다. `sideEffects: false` 는 이미 선언돼 있지만 아무 소용이 없다 —
생성자 안의 `new PinballLauncherController()` 는 번들러가 지울 수 없는 참조다.
`CORE_RENDERERS` 객체 리터럴도 마찬가지로 8종을 한 덩이로 묶어 둔다.

그래서 조건은 셋이다.

#### 조건 1 — 코어는 능력을 모른다

`Host` 생성자에서 등록 코드를 **전부 걷어낸다.** 코어에 남는 것은 빈 registry,
계약 타입, 무대 생애뿐이다. 코어가 어떤 렌더러·컨트롤러의 이름도 알지 못하면,
코어를 import 해도 그것들이 따라오지 않는다.

이것이 "항상 실리는 20" 의 정의다. **20은 크기로 정하는 게 아니라 의존으로 정해진다 —
능력을 하나도 참조하지 않는 것만 20에 들어간다.**

#### 조건 2 — 능력은 등록이 아니라 import 로 붙는다

```ts
registry.get('particles')                       // ✗ 번들러가 모른다. 전부 살려 둔다
import { particles } from '@aperi21/kit-particles'   // ✓ 번들러가 안다
```

문자열 키 조회는 정적 분석을 죽인다. 능력은 registry 에 넣지 않는다.

registry 가 남는 자리는 하나뿐이다 — **조각을 찾는 것.** 호스트는 글 속의
`{aperi21:<id>}` 문자열에서 조각을 찾아야 하므로 문자열 조회가 필연이고,
그건 이미 `registerBundleLoader` 라 lazy 가 보존된다. **거기까지다.**

#### 조건 3 — 선언과 정적 참조를 생성기가 잇는다

여기가 어려운 지점이다. `SceneGraph` 는 `{ type: 'body' }` 라는 **데이터**여서
번들러가 무엇이 쓰이는지 알 수 없다. 선언 우선(원칙 2)과 정적 분석이 정면으로
충돌한다.

해소는 생성기다. 저작자는 선언만 쓰고, 빌드가 선언을 훑어 import 목록을 뽑는다.

```ts
// 저작자가 쓰는 것 — 지금과 같다
scene: [{ type: 'body', ... }, { type: 'vector', ... }]

// pnpm gen 이 뽑아 주는 것 — 조각 옆에 생성된다
import { body, vector } from '@aperi21/vocab-core';
export const vocab = [body, vector];        // 정적 참조. 나머지 6종은 안 실린다
```

`scripts/gen-*.mts` 로 이미 하고 있는 일이라 새 문화가 아니다.

#### 증명 — 예산보다 음성 검사가 먼저다

숫자 예산(§R10)은 새는 것을 **늦게** 알려 준다. 즉시 잡는 것은 음성 검사다.

- 조각 하나만 넣은 최소 앱을 빌드해 산출물을 문자열로 훑는다
- 슬라이더만 쓰는 조각의 번들에 `pinball` 이 있으면 **실패**
- 자유 렌더만 쓰는 조각의 번들에 `renderTrajectory` 가 있으면 **실패**

"트리셰이킹이 될 것이다" 를 믿지 않고 **없음을 확인한다.** 이 검사가 `release:check`
에 들어가는 것이 §R10 예산표보다 앞선다.

#### 이 결정이 무르는 것

- **원칙 3의 범위가 좁아진다.** "레지스트리 경유" 는 조각 조회에만 남고, 능력에는
  적용하지 않는다. 원칙 3이 지키려던 것은 단일 인스턴스이지 조회 방식이 아니었다.
- **`new Host()` 한 줄의 편의가 사라진다.** 조각마다 자기가 쓸 능력을 넘겨야 한다.
  그 수고는 생성기가 대신 진다 (조건 3).

## 3. 요구사항 (엔진이 제공할 것)

### R1. 무대 — 그리지 않는 것

캔버스 한 장의 생애. **기본 화면은 비어 있다.**

- devicePixelRatio 스케일 · ResizeObserver · CSS px 좌표계
- RAF 루프, `dt` 상한(탭 복귀 폭주 방지), 배속·일시정지
- 프리롤 — N스텝을 그리지 않고 돌린 뒤 첫 프레임
- 가시성 정지 — `IntersectionObserver` + `visibilitychange`
- 마운트 후 세로 불변 (원칙 6), 화면비는 선언이 정한다
- `destroy()` 가 RAF·타이머·리스너·옵저버를 전부 거둔다 (C5)

### R2. 공간 — 매핑과 앵커

- 뷰포트 선언 → `toScreen` / `toWorld` / `scale`
- **화면 상수**: 선 두께·글자 크기는 배율에 딸려가지 않는다
- **월드 좌표는 선택이다.** 화면 좌표만으로 사는 구현체가 1급이어야 한다
- 앵커: 화면 모서리·월드 점·다른 요소의 경계에 붙이기

### R3. 입자

- 방출 간격 · 수명 · 위치 함수만 주면 도는 스트림
- **프레임 안 하위 시간 보정** (8이 여기서 버그 — 한 프레임에 여럿 방출할 때 순서 역전)
- **출생 번호 기반 안정 해시** (7이 여기서 떨림)
- 퇴출, 배열 순서 유지

### R4. 장(場)

- 검증된 난류 속도장 — 수명 있는 소용돌이 다발, 벽 근처 감쇠. 구현체는 `gain` 하나만 정한다
- 벡터장 샘플·이류
- 지수 성장/감쇠 `σ` 적용

### R5. 그리기 부품

- 채워진 영역 + 자유 곡선 경계 (수면·경사면)
- 잔상 획 — 위치 함수와 Δt를 주면 획을 긋는다
- 폴리라인·부채꼴·점선 치수선·눈금자
- 배경 깔린 칩

**어떤 부품도 색을 고르지 않는다.** 색·굵기·글꼴은 인자로 받는다. 자동 팔레트 배정
없음 (7·8 둘 다 "같은 색으로 둔 것이 이 조각의 주장" 이라고 적었다).

### R6. 글자

- 값 끼운 문안 + 3층 조회 (선언 문안 → locale → en 원본)
- **정박값 포매터** — 선언된 값에 충분히 가까우면 그 문자열을 쓴다
- 유효숫자 보존 (`3.70` 을 `3.7` 로 줄이지 않는다)
- 폭 재기, 넘치면 글자를 줄여 담기 (자리를 늘리지 않는다)
- **충돌 회피 배치** — "이 앵커에 붙이되 이 영역들은 피해라" 를 선언하면 엔진이 푼다

### R7. 움직임

- 감쇠 추종 스칼라
- 국면 시계 — 주기 안의 위상
- 선언적 자동 시퀀스: 정박값 목록 + 머무는 시간 + 보간 시간 → `t → 값`
- **수동 개입 후 N초 뒤 가장 가까운 정박값으로 복귀**
- 캡션 슬롯 **하나** + 교차 페이드 (슬롯이 하나라는 제약이 규범을 집행한다)

### R8. 조작기 — 배선과 생김새의 분리

값↔픽셀 매핑, 포인터 캡처, 클램프, 유휴 복귀는 엔진이. **생김새는 구현체가.**
지금 `controller/` 1131줄의 절반이 발사체 전용(`pinball-launcher`·`angle-dial`)인데,
그건 배선이 아니라 생김새다.

### R9. 강제하지 않을 것 (opt-in)

그리드 · 축 · 눈금 · 카메라 버튼 · 재생/일시정지/스크럽 · 제목 · 범례 · 툴팁 ·
상시 값 표시줄 · 자동 HUD · 시리즈별 자동 색 · 화면비.

**켜지 않으면 없다.**


### R10. 페이로드 — 필요한 것만 실린다

기능 요구와 같은 급이다. §2가 근거다.

- **커널은 정체성만 담는다.** registry + 계약 + 무대 생애. 능력은 밖으로.
- **L1 도구는 각각 독립 진입점**이고 모듈 레벨 상태·부수효과가 없다
  (`sideEffects: false`, named export). 트리셰이킹과 중복 허용이 동시에 가능해진다.
- **자유 렌더는 등록 없이 조각 안에서 그린다.** `Plugin` 계약을 태우지 않는다 →
  eager 로드가 사라지고, §1(가)의 "무거운 문" 도 함께 사라진다.
- **도메인 솔버는 조각이 선언한 것만 동적 로드한다.** 지금처럼 부트스트랩이
  전부 끌어오지 않는다.
- **카탈로그는 코드와 분리한다.** `aperi21-catalog.generated.ts` 는 순수 데이터라
  이미 지켜지고 있다. 수백 조각이 되어도 목록을 그리는 데 조각 코드를 로드하지 않는다.
- **예산을 게이트로 못박는다.** 숫자로 두지 않으면 지켜지지 않는다.

#### 예산 (gzip, 제안)

| 항목 | 예산 | 근거 |
|---|---|---|
| L0 커널 (항상) | **≤ 10 KB** | 지금 20.4 KB 에서 `controller`(1131줄)·`renderer`(633줄)를 들어내면 남는 크기 |
| L1 도구 하나 | **≤ 4 KB** | 조각이 보통 3~5개를 쓴다 |
| 조각 하나가 끄는 L1 총합 | **≤ 15 KB** | 위 곱 |
| 조각 자신 | **≤ 8 KB** | 지금 2.1~6.3 KB |
| **첫 조각 총합** | **≤ 35 KB** | 지금 44.3 KB |
| **두 번째 조각부터** | **≤ 12 KB** | 지금은 조각값 + eager 오염 |

**두 번째 조각부터가 진짜 지표다.** 한 문서에 조각이 여럿 박히는 것이 이 프로젝트의
전제이므로, 조각을 하나 더 놓는 값이 싸야 한다.

## 4. 구조 제안 — 층은 넷, 진입은 어디서든

지금 구조의 병목은 층이 하나뿐이라는 것이다. `선언 → 8종 어휘` 를 벗어나면 곧장
**캔버스 맨바닥**이라 342줄을 짜게 된다. 게임 엔진은 그렇게 생기지 않았다.

```
L3  선언        SceneGraph / BundleSchema          ← 저작 결정, 에디터의 대상
     ↓ 해석
L2  어휘        body vector surface trajectory …   ← L1로 만든 "기본 제공 부품"
     ↓ 호출
L1  도구상자    space draw particles field         ← 순수 함수·클래스, 캔버스를 소유하지 않음
                text motion caption input
     ↓ 위에서 돈다
L0  무대        캔버스 · 시계 · 생애 · 가시성        ← 아무것도 그리지 않는다
```

### 규칙 1 — 상위가 하위를 부른다. 하위는 상위를 모른다

`L1` 은 `L2`·`L3` 를 모른다. 그래서 `L1` 만 쓰는 구현체가 가능하다.

### 규칙 2 — 어느 층에서 시작해도 1급이다

| 진입 | 예 | 지금 |
|---|---|---|
| L3만 | `pressure-isotropy` (표준 어휘로 성립) | 가능 |
| L3 + L2 + 자체 L1 | `archimedes` (물·저울은 직접) | Plugin 등록이라는 무거운 문 |
| L1 + L0만 | `torricellis-law`, `laminar-vs-turbulent` | **불가능 — 그래서 엔진 밖에 있다** |

세 번째를 1급으로 만드는 것이 이 제안의 핵심이다.

```ts
// L1 + L0 진입 — 선언도 어휘도 없이
const stage = createStage(el, {
  aspect: 9 / 1,          // 화면비는 구현체가 정한다
  preroll: 460,           // 도착한 순간 이미 흐르고 있다
  chrome: 'none',         // 그리드도 카메라도 없다. 기본값이다
});

const dye = stage.use(particles({ rate: 160, life: 0.26, seed: 'dye' }));
const vortices = stage.use(turbulentField({ gain: g }));
const caption = stage.use(captionSlot());

stage.draw((g, t) => {           // g 는 L1 도구가 붙은 그리기 손잡이
  g.filled(tankPath, water);      // R5
  dye.each(p => g.streak(p.pos, p.prev, ink));   // R3 + R5
  g.chip(g.anchor.below(hole), fmt.anchored(re), muted);  // R5 + R6
});
```

`sims/**` 는 그대로 `L3` 로 두고, 조각은 `L0+L1` 로 들어온다. 같은 엔진, 다른 문.

### 규칙 3 — L2는 특권이 없다

지금 `CORE_RENDERERS` 8종은 호스트 안에 박혀 있고, 그 밖으로 나가려면 `Plugin` 을
만들어야 한다. 뒤집는다. **L2는 L1으로 작성된 기본 제공 묶음일 뿐**이고, 구현체가
같은 자리에 자기 것을 놓는 데 특별한 절차가 없다.

부수 효과로 `Primitive` 유니온의 선언만 있고 렌더러가 없는 17종
(`container`·`wave`·`vectorField`·`circuitElement` …)이 정리된다. 필요한 것은
L1으로 만들어 L2에 넣고, 나머지는 선언에서 지운다.

### 규칙 4 — 크롬은 전부 opt-in

`L0` 의 기본 화면은 비어 있다. 그리드·카메라·트랜스포트·범례·HUD 는 선언이 켜야
나온다. 이건 철학이 아니라 **§1(다)의 데모 잔재를 지우는 일**이다.

### 규칙 5 — L1 승격 기준은 두 번째 사례

원칙 4의 "공유 부품을 선제적으로 만들지 않는다. 두 번째 사례가 나온 뒤에 만든다" 를
`L1` 에 적용한다. §1(나) 표의 반복 횟수가 그 장부다. 지금 2회 이상이 11개다.

---


### 규칙 6 — external 의 기준은 크기가 아니라 상태

원칙 3의 "레지스트리를 담은 패키지를 inline 하지 않는다" 는 **모든 코드를 external 로**
가 아니다. 모듈 레벨 상태를 갖는 것만 external 이다. 순수 도구는 inline 되어도
정확성이 깨지지 않으므로 번들러가 자유롭게 판단하게 둔다.

`L1` 의 조건 셋 — 이것이 트리셰이킹의 전제다.

1. 모듈 레벨 상태 0 (인스턴스 상태는 무방하다)
2. `sideEffects: false`, import 만으로 아무 일도 일어나지 않는다
3. named export 만, 배럴 재수출로 남의 모듈을 끌지 않는다

### 규칙 7 — 등록은 값이 비싸다

registry 에 등록한다는 것은 **"누가 부를지 모르니 미리 로드해 둔다"** 는 뜻이고,
정적 분석을 죽인다. 그래서 registry 는 **loader 만 담고 구현을 담지 않는다.**
`registerBundleLoader` 가 이미 그 구조다 — 좋은 선례이니 예외를 만들지 않는다.

`installAperi21Plugins` 의 eager import 4건이 이 규칙의 유일한 위반이고,
§2.2(2)의 원인이다.

### 패키지 지도

| 패키지 | 담는 것 | 로드 | 인스턴스 |
|---|---|---|---|
| `@aperi21/kernel` | registry · 계약 · 무대(L0) | 항상 | **단일** (external + peer) |
| `@aperi21/kit-space` | 좌표 매핑 · 앵커 | 쓰는 조각만 | 자유 |
| `@aperi21/kit-draw` | 채움 · 잔상 · 칩 · 눈금자 | 〃 | 자유 |
| `@aperi21/kit-particles` | 방출 · 이류 · 수명 · 안정 해시 | 〃 | 자유 |
| `@aperi21/kit-field` | 난류 · 벡터장 | 〃 | 자유 |
| `@aperi21/kit-text` | 포매터 · 배치 · 충돌 회피 | 〃 | 자유 |
| `@aperi21/kit-motion` | 감쇠 · 국면 시계 · 시퀀스 · 캡션 | 〃 | 자유 |
| `@aperi21/vocab-core` | L2 표준 어휘 | 선언이 쓰면 | 자유 |
| `@aperi21/solver-*` | 도메인 물리 (강체·유체·광학·회로) | 조각 선언 기반 동적 | 자유 |

`kit` 과 `vocab` 은 상태가 없으므로 여러 빌드에 중복되어도 **틀리지 않는다.**
`kernel` 만 갈라지면 안 된다. 그래서 `kernel` 이 작아야 한다.

## 5. 이행 순서

반복 횟수 × 막힌 정도, 그리고 **나중에 하면 재작업이 되는 것**을 앞으로 당긴다.

| 순 | 할 일 | 근거 |
|---|---|---|
| 1 | §1(다) 강제 5건 제거 — 그리드·카메라·마진·바이어스 | 지우는 일이라 값이 싸다. 이게 없으면 무엇을 만들어도 위에 그리드가 얹힌다 |
| 2 | **eager 로드 끊기** — 자유 렌더를 `Plugin` 계약에서 떼어내 조각 안으로 | 즉시 11.5 KB 회수 + **선형 증가 차단**. §1(가)의 무거운 문도 함께 사라진다 |
| 3 | **커널/능력 분리** — `Host` 생성자의 자동 등록 15건을 걷어내고 `kernel` + `kit-*` 로 쪼갠다 (§2.4 조건 1·2) | 이것을 안 하면 패키지를 아무리 쪼개도 셰이킹은 0이다 |
| 4 | **음성 검사 + 예산 게이트** — 안 쓰는 능력의 고유 문자열이 번들에 **없음**을 확인 (§2.4) | 숫자는 늦게 알려 준다. 없음 확인이 먼저다 |
| 4b | 선언 → import 생성기 (§2.4 조건 3) | 이게 없으면 저작자가 import 목록을 손으로 관리하게 된다 |
| 5 | `kit-particles` + `kit-draw` | 반복 3회 둘. 조각 5개가 전부 여기서 막혔다 |
| 6 | `kit-text` (칩 · 포매터 · 충돌 회피) | 반복 3회 + 실제 버그 1건 |
| 7 | `kit-motion` + 캡션 | 조각 규범(`S-piece`)을 코드로 집행하는 자리 |
| 8 | `kit-field` (난류) | 8이 네 번 튜닝한 것. 값이 크지만 사례가 아직 하나 |
| 9 | `vocab-core` 를 kit 위로 재작성, 유령 프리미티브 17종 정리 | 위가 끝나야 재료가 생긴다 |

1~4가 **구조**이고 5~9가 **기능**이다. 순서를 바꾸면 안 된다.

1·2·3이 끝나는 시점에 `torricellis-law` 와 `laminar-vs-turbulent` 를 **엔진 위로 옮겨
붙여** 검증한다. 두 숫자가 이 설계의 점수다.

- 430줄 · 607줄이 얼마나 줄어드는가 (기능)
- 조각 하나를 여는 gz 가 44.3 KB 에서 얼마로 내려가는가 (페이로드)

## 6. 규칙 체계에 반영할 것

- **원칙 3 개정** — "레지스트리를 담은 패키지를 inline 하지 않는다" 에 §2.3의 기준을 명시한다:
  external 의 조건은 **모듈 레벨 상태의 유무**이지 크기가 아니다
- **C6 신설 검토** — 페이로드 관심사. `sideEffects` · 배럴 재수출 · registry eager 등록
- `rules/INDEX.yaml` 예약 항목 **`S-piece`** — 대상이 생겼으므로 신설 가능
- `S-sim` / `S-render` 의 "자유 렌더 계층" 절 → `L1` 진입을 정식 계층으로 승격
- 원칙 4 개정 검토 — "프리미티브는 어휘, 탈출구는 1급" 에서 **탈출구가 1급이 되려면
  탈출한 자리에도 도구가 있어야 한다**는 조항 추가
