# 주제 ↔ 조각 간극 장부

주제가 약속한 것과 조각 화면이 실제로 하는 것의 **차이**를 적는 곳이다.

`tasks/engine-requirements/gap-ledger.md`(G) 와 성격이 다르다. 그쪽은 **엔진 어휘**가
모자라 조각이 근사한 자리이고, 이쪽은 **주제와 조각 사이**가 벌어진 자리다. 원인이
엔진일 수도 있지만 아닐 때가 더 많다.

## 왜 개념 배치에서 적는가

개념 메타를 쓰는 일이 `topics.yaml` 의 주제 설명과 조각 화면을 **나란히 놓고 읽는
유일한 작업**이다. 개념의 `definition` 은 화면이 실제로 하는 주장으로 써야 하므로,
주제 설명이 그보다 넓으면 쓰는 사람이 반드시 알아차린다. 그때 적지 않으면 그 사실은
개념 파일 안에 묻히고 아무도 다시 찾지 않는다.

## 무엇을 올리는가 — 바

**주제 설명을 읽고 온 독자가 기대할 주장을 화면이 하지 않을 때**만 올린다.

- 올린다 — 「기울기가 가속도, 넓이가 변위」라고 적힌 주제인데 화면은 넓이만 말한다
- 올린다 — 「세 식」이라고 적힌 주제인데 화면에 식이 없다
- 올리지 않는다 — 화면이 예쁘지 않다, 값이 하나뿐이다, 조작기가 없다
- 올리지 않는다 — 엔진 어휘가 모자라 모양이 조금 다르다 (그것은 G 장부)

## 갈래 — 적되 판정하지 않는다

| 갈래 | 뜻 |
|---|---|
| `설명` | 주제 설명이 실제보다 넓게 적혀 있다. 설명을 고치면 끝난다 |
| `조각` | 주제가 맞고 조각이 덜 보여 준다. 조각을 보강해야 한다 |
| `엔진` | 조각이 덜 보여 준 이유가 엔진 어휘다. G 장부와 이어진다 |

쓰는 사람은 **가장 그럴듯한 갈래 하나**를 적는다. 최종 판정은 사람이 장부를 보고 한다 —
「세 식」이 설명 과함인지 조각 부족인지는 그 주제를 어디까지 다룰지의 결정이라
조각을 읽어서는 나오지 않는다.

## 쓰는 법 (배치 에이전트)

묶음마다 **자기 파일 하나**에 행만 적는다. 여러 에이전트가 한 파일에 쓰면 거기가
충돌 지점이 된다.

```
tasks/topic-gaps/entries/<분과>-<묶음번호>.md
```

행 서식 — 파이프 다섯 칸. 한 줄에 하나.

```
| <주제 id> | <주제가 약속한 것> | <화면이 하는 것> | <개념에서 처리한 방식> | <갈래> |
```

간극이 없으면 파일을 만들지 않는다. **없는데 만들어 빈 표를 남기지 않는다.**

## 모으기

```sh
pnpm gap:ledger      # entries/*.md → LEDGER.md (T 번호 부여)
```

번호(`T01` …)는 모을 때 붙는다. 분과 순서(`topics.yaml`)와 파일 이름순으로 고정이라
다시 모아도 같은 번호가 나온다. 행이 늘면 뒤에 붙는다.

## 보충 작업

배치가 전부 끝난 뒤 `LEDGER.md` 를 놓고 **한 건씩 사람이 방향을 잡는다.** 갈래마다 할
일이 다르다.

판단은 `triage/*.md` 에 적는다 — 「설명」 갈래는 분과 묶음 파일(`mechanics.md` 등),
「조각」 갈래는 `pieces-*.md`. 기준은 **「시각화가 유리한가」** 이고, 갈래가 무엇이든
뒤집힐 수 있다. 실제로 100건 중 「조각」 18건에서 11건이 설명 수정으로 내려갔다.

판단에서 나온 **「조각 보강」은 `BOOST.md` 에 모은다.** 거기가 순서와 상태를 쥐는
자리이고, 그 문서는 생성물이 아니라 손으로 고치는 목록이다.

- `설명` → `docs/topics/topics.yaml` 의 `desc` · `visualNote` 를 화면에 맞춘다
- `조각` → 조각을 보강한다. **보강하면 개념 메타를 다시 쓴다** — `definition` 이 바뀌면
  `definitionHash` 가 바뀌고 호스트가 그 개념만 다시 임베딩한다
- `엔진` → G 장부로 넘긴다
