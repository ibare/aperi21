## 1. 배포 — 지금 잠복 중인 폭탄

### 1-1. 단일 registry 인스턴스 (최우선)

FACET `CLAUDE.md` 원문:

> **단일 registry 인스턴스 제약**: `bootstrap`·`host-tiptap-bundle` 은 `@ffacet/core` 를
> rollup `external` + `peerDependency` 로 둔다. core 를 inline 하면 **registry 가 갈라져
> bootstrapFacet 등록 facet 을 runFacet 이 못 찾는다.**

우리 구조가 정확히 그 반대다. `host-tiptap-bundle` 은 `@aperi21/host` 를 **inline** 하고,
그 host 안의 `packages/host/src/runtime/bundleRegistry.ts` 는 모듈 레벨 `Map` 싱글톤이다.

- **지금은 안 터진다** — 외부 진입점이 `host-tiptap-bundle` 하나뿐이다.
- **터지는 조건** — methii 가 `@aperi21/react`(Embed) 나 두 번째 번들을 함께 설치하는 순간.
  각자 자기 Map 을 들고, `registerBundleLoader` 로 등록한 sim 을 상대편 `runBundle` 이
  못 찾는다. 타입은 통과하고 예외도 안 나고 "등록 안 됨" 만 뜬다.

FACET 해법: `core` 를 별도 발행 → 번들 쪽은 `external` + `peerDependencies` →
호스트가 단일 인스턴스를 설치해 공유. 발행 순서도 peer 때문에
`core → bootstrap → host-tiptap-bundle` 로 고정됐다.

우리에게는 `@aperi21/host`(+`schema`) 를 `core` 격으로 발행 대상에 올리는 결정이다.
**소비자가 하나뿐인 지금이 가장 싼 시점.**

### 1-2. `workspace:` 프로토콜은 두되 `pnpm publish` 가 변환하게 한다

우리 CLAUDE.md 는 *"publish 대상 패키지의 `dependencies` 에 `workspace:*` 를 두지 말 것"*
이라는 회피책을 쓴다. FACET 은 반대로 갔다.

> **`pnpm publish` 만 사용** (`npm publish` 금지). `workspace:^` 를 npm semver 로
> 변환하는 건 pnpm 뿐이다. `npm publish` 는 workspace 프로토콜을 그대로 올려 깨진
> 의존을 발행한다.
> peer range 는 `workspace:^` 로 선언 → 발행 시 `^<현재버전>` 으로 자동 변환. 손수정 불필요.

우리 회피책은 패키지가 하나일 때만 성립한다. 1-1 을 하면 peer 가 생기므로 이 규약이 필요해진다.

### 1-3. publishConfig 로 src↔dist 분리

> `main`/`types`/`exports` 는 `./src/*.ts` 를 가리켜 **워크스페이스 내부는 빌드 없이
> 소스 직참조**하고, `publishConfig.{main,types,exports}` 가 publish 시에만 `./dist/*` 로
> 오버라이드된다.

우리는 `main` 이 `dist` 고정이라 내부 소비자가 생기면 항상 빌드 산출물을 봐야 한다.
지금은 내부 소비자가 없어 무해하지만 패키지가 늘면 비용이 된다.

### 1-4. 발행 전 게이트 4단

우리는 typecheck 하나. FACET 은:

1. `pnpm -r typecheck`
2. `pnpm test`
3. **`pnpm pack` 으로 tarball 검증** — publishConfig 오버라이드 적용, `workspace:^`→semver
   변환, `src` 누출 0, 발행 비대상 의존 누출 0
4. rule-guard 감사 (의존 일방향·lazy 보존·단일 인스턴스)

3번이 실제로 잡은 사고가 커밋에 남아 있다:

| 커밋 | 내용 |
|---|---|
| `c726076` | 발행본에서 죽던 메시지 번들 로더 복구 |
| `c53f389` | 발행본 d.ts 가 타입을 전달하도록 수정 |
| `a8cfe7a` | host-tiptap-bundle 빌드에 json 플러그인 누락 |

**셋 다 워크스페이스에서는 멀쩡하고 발행본에서만 죽는 종류다.**
우리 0.1.0 도 같은 검사를 통과한 적이 없다.

## 2. 컨셉 정합성 — 저작자가 손댈 수 있는가

### 2-1. 화면 문자열: 코드에는 키만 (FACET 규칙 C10)

FACET 이 원칙 2 에 새로 넣은 문장:

> `FacetJson` 은 장차 에디터로 불특정 다수가 만드는 선언이다. **시각화가 무엇이라
> 말하는지도 저작 결정이다.** 문안이 projector/view 코드에 있으면 저작자가 손댈 수 없다.
> 문자열을 코드 안 카탈로그로 옮기는 것만으로는 부족하다 — 그것도 여전히 코드다.

우리 실측 결과. sim 선언(`schema.ts`)의 `{ko, en}` 은 잘 되어 있으나 **런타임 UI 가
코드에 박혀 있다**:

```
packages/react/src/embed/CameraControls.tsx:35   {ko ? '카메라' : 'Camera'}
packages/react/src/embed/EnergyHUD.tsx:68        {ko ? '운동' : 'KE'}
packages/react/src/embed/InfoPanel.tsx:11        t: { ko: '시간', en: 't', ... }
packages/host-tiptap/src/node-view.ts:38         box.style.background = '#FAECE7'
```

삼항 연산자는 세 번째 언어를 받을 수 없고, 저작자는 "운동" 을 "운동에너지" 로 바꿀 수 없다.

**3층 조회** (그대로 이식 가능):

```
1. FacetJson.messages[key]   저작자가 정한 문안       ← 언제나 이김
2. locale 번들[key]           registerMessages 로 주입
3. 코드의 en 원본             호출부 리터럴 fallback
```

3층이 항상 있으므로 번역이 하나도 없고 저작자가 아무것도 쓰지 않아도 화면은 en 으로
온전히 뜬다. 조회는 `tr(key, 'en 원본', vars)` 하나이고, **러너가 조회기를 하나만 만들어
view 와 projector 양쪽에 주입**한다 (각자 만들면 한 화면에서 문안 출처가 갈린다).

부수 효과: 추출기(`scripts/gen-messages.mts`)가 en 원본 리터럴을 긁어 `messages/en.json`
을 만들고 **고아 키와 미번역 키를 보고**한다. 단 en 원본은 호출부에 **리터럴로** 둬야
한다 — 상수로 빼면 추출 대상에서 누락된다.

#### 표식이냐 문안이냐 — 물리 도메인에 특히 중요

번역하면 오히려 화면과 어긋나는 것들을 가리는 4단계 판정:

1. **도형에 새겨진 글자인가** (`IN`/`OUT`, LED 라벨) → 표식, 키 만들지 않음
2. **원어 그대로 통용되는 용어인가** (`head`/`NULL`/`next-hop`) → 표식
3. **수식·기호 표기인가** (`det = +1.00`, `α`) → 표식
4. 그 외, 조사·어미가 붙거나 어순이 언어마다 달라지는 것 → **문안**, 키

경계: **소문자 도식 라벨 한 단어는 표식, 값이 끼어드는 조립문은 문안.**
`capacity` 는 표식이지만 `Size: {n} / {cap}` 은 문안.

우리 도메인은 3번이 압도적이다 — `m/s²`, `EMF`, `KE`/`PE`, `y_max`, `t_f` 는 전부 표식.
이 판정표 없이 시작하면 수식까지 번역 키로 만들어 화면이 망가진다.

값 삽입은 **`{name}` 플레이스홀더 + `vars`**. 문자열 이어붙이기나 템플릿 리터럴 보간을
쓰면 어순이 다른 언어에서 문장이 깨진다.

### 2-2. 선언에 없으면 저작자가 못 바꾼다

`packages/host/src/runtime/runBundle.ts:114` — `wrapper.style.height = '360px'` 하드코딩.

FACET 은 `canvas: { width?, height, fit? }` 를 JSON 에 두고 **러너가 껍데기를 만들어
`params.canvas` 로 넘기는** 방식으로 풀었다 (`dc2d0ee` "캔버스 껍데기를 러너가 만든다").
우리도 껍데기는 러너가 만들지만 **치수가 선언이 아니다.**

FACET 이 그 과정에서 발견한 함정 둘 — 우리도 그대로 밟을 수 있다:

- **세로는 마운트한 뒤 바뀌지 않는다.** 호스트(Tiptap NodeView)는 높이를 정하지 않으므로,
  높이가 바뀌면 **글 안에 박힌 그림의 위아래 문단이 밀린다.** 읽는 사람에게는 글이
  흔들리는 것으로 보인다. 내용에 따라 커지는 그림은 흔한 크기만큼 미리 자리를 잡고,
  **넘치면 간격을 줄여 담는다** (높이를 늘리지 않는다).
  - 우리는 360px 고정이라 지금은 안전. 단 `autoFrame` 카메라가 궤적에 맞춰 프레이밍하므로
    "높이를 내용에 맞추자" 는 요구가 나오는 순간 이 함정에 들어간다.
  - FACET 은 완제품 둘이 빠졌고(229→291, 80→260) `canvas-height.test.ts` 가 전수로 잰다.
- **컨테이너를 비우면 캔버스가 떨어져 나간다.** 러너가 캔버스를 먼저 붙이고 mount 를
  부르므로, mount 첫 줄의 `container.textContent = ''` 가 화면을 통째로 지운다.
  타입도 통과하고 예외도 안 나고 그림만 안 보인다. 열하나가 빠졌고 **일곱은 발견되지
  않은 채 커밋됐다** → `canvas-attach.test.ts` 신설.

### 2-3. 자동 시작을 선언에 둔다

`08932c4` "feat(core): FacetJson.autoStart 로 자동 시작을 선언에 둔다".
우리 스키마에 대응물 없음 (grep 0건). 글 안에 박히는 시각화는 "누가 언제 시작하는가" 가

단, 같이 배운 반례 — **뷰포트 진입 시 자동 재생은 두지 않는다.**
*"읽는 흐름을 방해하고, 여러 조각이 박힌 글에서는 독자가 도달하기 전에 전부 끝나 있게 된다."*

## 3. 공유 부품의 실패 판정 — 우리에게 가장 아픈 것

FACET 은 2026-09-09 에 원칙 6 을 갈아엎었다 (`f639355`).

> **stage view 는 예외가 아니라 기본이다.** 새 facet 은 자기 시각화를 자기 패키지 안에
> 직접 그린다.
> **공유 View 를 새로 만들지 않는다.** 빌트인 카탈로그(`core/src/views/*`)는 코드 재사용과
> 품질 상향을 노린 장치였으나, **대량 생산에서 유사 화면 복제를 낳아 실패로 판정됐다.**
> 같은 부속을 물려받은 facet 들이 서로 닮은 화면이 되었고, **그것은 시각화의 값을 깎는다.**
> 걷어낼 예정이며 그것을 쓰는 완제품 스물다섯도 다시 만든다.
> 지금은 105 중 101 이 stage view 를 가지므로 (빌트인으로 되는 것의) 목록에 뜻이 없다.

### aperi21 은 정확히 그 구조다

- 우리 sim 은 전부 선언이고, 그림은 `packages/host/src/renderer/primitives/`
  (body·gauge·graph·marker·surface·trajectory·vector) 가 그린다.
- **자기 렌더러를 가진 sim 은 0개.** 렌더러 확장은 plugin 층에만 있다
  (`plugin-optics` 가 `primitiveTypes: ['ray','opticalElement']` 선언).
- 스키마의 탈출구는 `shape:'custom'` + `customPath`(SVG path 문자열) 와 직렬화 불가능한
  `fn` 뿐 — 사실상 탈출구가 없다.

### 다만 그대로 받아들이면 안 된다 — 도메인 차이

- 알고리즘 시각화에서 "배열"·"트리" 는 **표현 관습**이다. 같은 bar-chart 를 쓰면 정말로
  닮은 화면이 된다.
- 물리에서 "공"·"벡터"·"지면" 은 **실재하는 대상**이다. 두 sim 이 같은 화살표로 힘을
  그리는 건 복제가 아니라 정확성이다.
- FACET 도 예외 둘을 남겼다 — `control-bar`(화면이 아니라 조작 경로), `code-view`(완제품의
  산출물 그 자체).

### 결론: 폐기가 아니라 탈출구의 1급 승격

- `sims/<cat>/<name>/src/<name>-stage.ts` 를 정식 계층으로 신설. 프리미티브로 표현
  불가능한 시각화를 sim 이 직접 그리고 자기 렌더러를 등록한다.
- 판정 기준은 FACET 의 것을 그대로: **"이 질문의 동사가 무엇이고 그것이 화면에서 어떻게
  일어나는가."** 프리미티브 조합으로 그 동사가 안 나오면 직접 그린다.
- **실제로 공유할 view 는 두 번째 사례가 나온 뒤에 만든다.** FACET 의 `core/views` 에는
  `linked-list-chain`·`ordered-list`·`iso-bar` 가 **쓰임 없이 만들어져 아무도 쓰지 않는
  상태로** 남아 있다. 우리 프리미티브 목록도 sim 3개 기준으로는 선제적으로 만들어진 것들이다.

## 4. 볼륨 확대 — 이미 실패한 길을 다시 걷지 않도록

FACET 은 "호스트 글에 붙을 자리가 없다"(샘플 커리큘럼 노드 28칸 중 10칸만 채워짐)는
문제에서 출발해 **두 방식을 시험하고 하나를 폐기**했다. methii 연동이 본격화되면 우리도
같은 문제를 만난다.

### 폐기된 길 — 발췌(aspect)

기존 facet 의 algorithm·projector·view 를 공유하고 `initialData` 와 `layout` 만 좁힌
하위 시각화 15종. `11378b1`(시험) → `60226b7`(폐기), **하루 만에 되돌렸다.**

> **선언만으로 만들어진다는 점이 장점처럼 보였는데, 그것이 바로 한계였다.**
> 근본 원인은 **축척이 그대로**라는 데 있었다. `-node` 는 "노드를 확대한 그림" 이 아니라
> "노드가 1개인 연결 리스트" 였다. 같은 stage view, 같은 좌표계, 같은 카드 크기 — 데이터만
> 작다. **명세를 부모에게서 물려받으면 그림도 물려받는다.**
> 선언만으로 되는 일은 데이터 축소뿐이고, **데이터 축소는 설명이 되지 않는다.**

**우리에게 이 유혹은 구조적으로 준비되어 있다** — 스키마에 이미 `variants`(단순/직렬/병렬)
와 `autoViews` 가 있어서 "projectile 에 initialData 만 바꾼 변형 10종을 찍자" 가 자연스럽다.
FACET 이 그 길을 가서 15종을 만들고 버렸다.

### 채택된 길 — 조각(piece)

정의가 바뀐다:

- 작다 = 데이터가 적다 (X)
- **작다 = 말하는 것이 하나다 (O)**

만드는 순서:

1. 한 덩어리를 설명할 때 **글이 멈추는 지점**을 나열한다.
2. 각 지점에 **"그림 없이 그 문장을 이해시킬 수 있는가"** 를 묻는다. 문장으로 충분하면
   만들지 않는다. 그림이 훨씬 빠르면 값어치 있고, 그림 없이는 사실상 불가능하면 필수다.
3. 남은 것마다 **답하는 질문 한 문장**을 쓴다. 그 문장이 곧 명세이자 검수 기준이다.

물리로 옮기면 — "포물선 운동" 하나가 아니라:

- *왜 45°에서 사거리가 최대인가*
- *공기저항이 있으면 왜 정점이 앞으로 당겨지는가*
- *달에서 같은 힘으로 던지면 무엇이 달라지는가*

각각이 독립 sim 이고, 축척·라벨·운동을 질문이 정한다.

**레고 조립은 폐기됐다**: *"공유는 제작 측이 아니라 소비 측에서 일어난다 — 조각 하나를
여러 주제의 글이 가리킨다."*

### 조각 규범에서 우리에게 그대로 적용되는 조항

- **질문 하나에만 답한다.** 캡션이 둘이면 조각이 둘이라는 신호.
- **형태는 질문이 정한다.** 앞 조각의 레이아웃·좌표계·헬퍼를 출발점으로 삼지 않는다.
- **누르지 않으면 완성되지 않는 화면을 만들지 않는다.** 자동 재생만 보고 지나가도 화면은
  할 말을 마쳐야 한다. 다시 보기는 놓친 사람을 위한 것이지 진행에 필요한 조작이 아니다.
- **개념을 설명하는 상시 캡션을 두지 않는다.** 바로 위 글이 이미 한 말을 화면에서
  되풀이하는 것이 된다.
- **전제는 글이 밝힌다. 화면에 각주를 두지 않는다.** 조각은 여러 글에서 불리는데 각주는
  고정이라, 어떤 글에서 군더더기가 되는지를 조각이 정할 수 없다.
- **화면에 쓰는 값은 실측한다.** 지어내지 않으면 밝힐 전제도 줄어든다.
- **그 폭을 채운다.** 요소 크기를 상수로 못박고 남는 폭을 여백으로 버리지 않는다.
  크기는 캔버스에서 역산하고 상수로는 **상한**만 둔다.

### 대량 생산의 관성, 그리고 계측기

조각 9종을 만든 뒤 FACET 이 발견한 것:

> 넷이 질문과 무관하게 같은 모양이 되어 있었다 — 앞 조각의 골격을 복사하고 내용만 갈아
> 끼운 결과다. `text()` 헬퍼가 여덟 벌 바이트 단위로 같았고, **운동이 전부 `opacity`/`fill`
> 전환뿐이라 위치가 변하는 애니메이션이 한 건도 없었다.**
> "접힌다"·"들어간다"·"번진다"·"갈라진다" 가 전부 "페이드인" 으로 번역되면 조각은
> 시각화가 아니라 순서대로 나타나는 다이어그램이 된다.

그래서 `scripts/piece-inertia.mjs` 를 만들었다. 재는 것 넷:

1. **코드 유사도** — stage 파일을 정규화(주석·문자열·숫자 제거)해 토큰 3-gram 자카드
2. **좌표 겹침** — 숫자 상수 집합의 자카드
3. **그림 어휘** — 묶음 전체가 쓴 SVG 원소 종류
4. **운동** — 위치/변형 애니메이션을 쓰는 조각 수 (`opacity` 만으로는 운동이 아니다)

스크립트 헤더: *"두 번 겪었고 둘 다 눈이 아니라 실측으로 잡았다. 사람에게 보이기 전에
여기서 먼저 거른다."*

**우리는 sim 이 3개라 아직 관성이 없다. 10개를 넘기기 전에 계측기를 먼저 두는 것**이
이 기록의 교훈이다.

## 5. 프로세스

### 5-1. rules/ 3계층

```
rules/
  principles.md          ← 6원칙, 항상 로드
  concerns/C1~C10.md     ← 관심사, 트리거 로드
  specifics/S-*.md       ← 6도메인, 트리거 로드
  INDEX.yaml             ← 경로/패턴/import 트리거 레지스트리
```

설계 의도가 명확하다:

> ESLint 를 도입하지 않는다. tsc(strict) 로 커버되는 항목은 Rules 에 넣지 않는다.
> Rules 는 **tsc 가 잡을 수 없는 의미/맥락 영역**에만 집중한다.

각 규칙은 MUST / MUST NOT / PREFER / Exception 으로 나뉘고, **위반이 발견된 실제 사건이
규칙 본문에 근거로 붙어 있다** — "38곳이 갈렸고 그중 하나가 폭을 CSS 로만 줘서 300px 로
떨어져 그림이 절반 아래로 눌렸다", "reset 이 29곳에 쓰이는 동안 라벨이 세 갈래로 어긋나
있었다". 규칙이 훈계가 아니라 사고 기록이다.

### 5-2. 규칙을 회귀 테스트로 고정

가장 실무적으로 유용한 부분. 이 규칙 위반들은 **타입도 통과하고 예외도 안 나서** 테스트로만
잡힌다.

| 테스트 | 잡는 것 | 계기 |
|---|---|---|
| `canvas-attach.test.ts` | CanvasView 전수 마운트 후 캔버스 잔존 | 열하나가 빠졌고 일곱은 미발견 커밋 |
| `canvas-height.test.ts` | 재생 중 세로 변동 금지 (전수) | 완제품 둘이 229→291, 80→260 |
| `piece-first-advance.test.ts` | 첫 조작의 의미가 갈리지 않는지 | 조각 스물 중 셋이 달랐음 |

### 5-3. 생성물 스크립트

`messages:gen`(추출·고아 키 보고) / `screen:gen` / `concept:audit`(개념 선언 감사기) /
`catalog:gen`. 우리는 `catalog:gen` 하나뿐.

### 5-4. authoring 패키지 — 호스트가 "어느 시각화를 쓸지" 고르게 하는 층

`6adbe77` 로 신설. 우리에게 대응물이 없고, methii 연동이 깊어지면 반드시 필요해진다.

> 1. **글에 들어갈 시각화 선택** → `surface`(definition + exemplarKeywords). 호스트가
>    임베딩해 글↔개념 매칭에 쓴다. `definitionHash` 로 **바뀐 것만 재임베딩**한다.
>    `briefing.avoidWhen` 은 그 검색이 만드는 오검출을 되돌리고, `briefing.useWhen` 은
>    **같은 개념에 화면이 둘 있을 때** 어느 쪽인지를 가린다. definition 이 겹치는 둘
>    사이에서 검색은 답을 낼 수 없다.
> 2. **선택된 시각화의 내용을 writer 에게 전달** → `briefing`(observable / screen /
>    avoidWhen / contrastWith).
>
> 이 패키지는 **어떤 워크스페이스 패키지도 import 하지 않는다.** 소비자가 브라우저
> 런타임이 아니라 **호스트의 LLM 서버**라서, 개념 메타를 읽는 대가로 View/transpiler
> 코드가 딸려오면 안 되기 때문이다.

우리 `docs/01-catalog.json` + `getAperi21Catalog()` 는 "무엇이 있는가" 만 답한다.
**"언제 쓰면 안 되는가"(`avoidWhen`)와 "비슷한 것 중 왜 이것인가"(`useWhen`)가 없다.**

## 6. 받아들이지 않아도 되는 것

- **IR / 6개 언어 transpiler** — 알고리즘 고유. 물리에 대응물이 없다. 굳이 찾으면
  "수식 패널" 이지만 별개 설계다.
- **10개 언어 전수 번역** — FACET 도 단서를 달았다: *"조각이 외부 호스트에 채택되거나
  20종을 넘으면 10개 언어로 맞춘다."* 우리는 ko/en 으로 충분하다.
  **단 3층 조회 구조는 지금 넣어야** 나중에 언어만 얹으면 된다.
- **Mechanism 추상(coroutine/reactive)** — 우리 `TimeEngine`(linear/static/steady-state)이
  같은 자리를 이미 채운다. 다만 reactive 의 두 성질(**mount 시 스스로 시작**, **걸음 간격을
  선언에서 받기**)은 우리에게 없고, 글에 박히는 시각화에는 필요하다.
- **Baden MCP 연동** — 도구 선택 문제이지 설계 인사이트가 아니다.
